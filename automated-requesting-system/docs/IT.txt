Here are the key documents that senior developers create:

---

## 1. Technical Documentation

| Document | What it covers |
|---|---|
| **README.md** | Project overview, setup, how to run |
| **API Documentation** | Endpoints, request/response, auth |
| **Architecture Document** | System design, tech stack decisions |
| **Database Schema** | Tables, relationships, data types |
| **Tech Stack Document** | Why each technology was chosen |

---

## 2. Planning Documents

| Document | What it covers |
|---|---|
| **System Design Doc** | How the whole system is structured |
| **Technical Specification** | Detailed breakdown of a feature before building |
| **RFC (Request for Comments)** | Proposing a technical change for team review |
| **Roadmap** | What gets built and when |
| **Estimation Document** | Time and resource estimates per feature |

---

## 3. Process Documents

| Document | What it covers |
|---|---|
| **Onboarding Guide** | How new devs set up and understand the project |
| **Contribution Guide** | How to submit code, branch naming, PR rules |
| **Code Review Checklist** | Standards every PR must meet |
| **Git Workflow Doc** | Branching strategy (GitFlow, trunk-based, etc.) |
| **Deployment Guide** | Step by step how to deploy the app |

---

## 4. Code-Level Documentation

```javascript
/**
 * Authenticates a user and returns a JWT token
 * 
 * @param {string} email - User's email address
 * @param {string} password - User's plain text password
 * @returns {Promise<string>} JWT token
 * @throws {AuthError} If credentials are invalid
 */
async function loginUser(email, password) {
  // ...
}
```

- **Inline comments** — explaining why, not what
- **JSDoc / JavaDoc** — function signatures and descriptions
- **Code changelog** — what changed and why

---

## 5. Security & Operations

| Document | What it covers |
|---|---|
| **Security Policy** | How sensitive data is handled |
| **Environment Variables Guide** | What each `.env` variable does |
| **Incident Report** | What went wrong, root cause, fix applied |
| **Postmortem** | Deep analysis after a major bug or outage |
| **Runbook** | Step by step for handling known issues |

---

## 6. Testing Documents

| Document | What it covers |
|---|---|
| **Test Plan** | What will be tested and how |
| **Test Cases** | Specific scenarios and expected results |
| **QA Checklist** | Manual checks before every release |
| **Bug Report Template** | Consistent format for reporting issues |

---

## Most Important Ones to Start With

If you're building a project right now, focus on these first:

```
1. README.md          — always, every project
2. API Docs           — if you have a backend
3. .env.example       — list all environment variables
4. Architecture Doc   — even a simple diagram
5. Deployment Guide   — so anyone can deploy it
```

## Types of Diagrams Developers Make

### 1. System Architecture Diagram
Shows how all parts of your app connect:
```
[React Frontend] → [Express API] → [MongoDB]
                              ↓
                         [Electron App]
```

### 2. Flowchart
Shows logic flow of a feature:
```
User Login → Validate Input → Check DB → 
  Found? → Generate JWT → Return Token
  Not Found? → Return 401
```

### 3. ERD (Entity Relationship Diagram)
Shows database structure and relationships:
```
User ──< Orders >── Products
```

### 4. Sequence Diagram
Shows how components talk to each other over time

### 5. UML Class Diagram
Shows classes, properties, and methods

## Best Standards to Follow

| Standard | What it is | Resource |
|---|---|---|
| **C4 Model** | 4-level system architecture standard | c4model.com |
| **UML** | Universal diagram language | uml.org |
| **ERD (Crow's Foot)** | Database relationship notation | standard in most DB tools |
| **BPMN** | Business process flow diagrams | bpmn.org |

**C4 Model is most recommended** — it breaks your system into 4 levels:
```
Level 1 → System Context    (big picture)
Level 2 → Container         (apps, databases)
Level 3 → Component         (inside each container)
Level 4 → Code              (classes, functions)
```

## Mermaid.js Example (diagrams in code)

You can write diagrams directly in your markdown docs:

```mermaid
graph TD
    A[React Frontend] -->|HTTP Request| B[Express API]
    B -->|Query| C[MongoDB]
    B -->|Response| A
    A -->|Loaded in| D[Electron App]
```

GitHub renders Mermaid diagrams automatically in `.md` files — great for keeping diagrams inside your repo.
